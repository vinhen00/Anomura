# Two-Pass Analysis + Substitution — Design Document

**Date:** 2026-11-10
**Status:** Draft
**Supersedes:** `post_expansion_substitution.md` (query override approach)

---

## 1. Problem Statement

The current `CrateIntercept` operates in `after_crate_root_parsing`, which fires **before** macro expansion. Items generated by `macro_rules!`, derive macros, and proc macros are invisible. The previous attempt to solve this via a `resolver_for_lowering_raw` query override (see `post_expansion_substitution.md`) ran into fundamental issues: `DUMMY_NODE_ID` panics, `DefId` registration complexity, and fragile interaction with rustc's post-expansion invariants.

The core insight is: **reading the expanded/typed AST is easy and safe; mutating it post-expansion is hard and fragile.** By separating reading from writing into two passes, we get the best of both worlds.

## 2. Architecture Overview

```
cargo mock test
  │
  ├─ Pass 0: Discover (test crate) — unchanged
  │    → finds mock_crate!(fns), mock_fn!, mock_method! invocations
  │    → identifies crate targets, IPC back to cargo-mock
  │
  └─ Pass 1+2: Substitution driver (per mock_crate target)
       │
       │  Within SubstitutePlugin::run(), two sequential rustc_run() calls:
       │
       ├─ rustc_run #1: AnalysisPass (read-only)
       │    → after_expansion: collect CrateApiModel from expanded AST
       │    →   (syntactic: signatures, fields, module tree, fully qualified types)
       │    → after_analysis: enrich model with type info from TyCtxt
       │    →   (trait impls, blanket impls, generics, lifetimes, repr info)
       │    → Compilation::Stop (skip codegen)
       │    → produces: AnalysisModel (in-memory)
       │
       └─ rustc_run #2: CrateIntercept (generative)
            → after_crate_root_parsing: receives AnalysisModel
            →   1. Keep scaffolding items (use, const, static, type alias,
            →      extern crate, extern blocks, macro defs)
            →   2. Remove all other items (fn, struct, enum, trait, impl, mod, macro calls)
            →   3. Regenerate removed items from the AnalysisModel
            →      (mock dispatch bodies, PhantomData fields, convenience API)
            →   4. Preserve original module structure
            → Compilation::Continue (full compile of regenerated crate)
```

Both `rustc_run` calls happen in the same OS process (inside `SubstitutePlugin::run()`),
so the model stays in memory — no serialization needed.

## 3. Execution Flow in Detail

### 3.1 SubstitutePlugin::run() changes

```rust
fn run(
    crate_name: String,
    compiler_args: Vec<String>,
    plugin_args: &Vec<String>,
) -> rustc_interface::interface::Result<()> {
    // ... existing arg setup (--extern context, --cap-lints) ...

    if is_mock_crate_target {
        // Pass 1: Analysis (read-only, full compile through type checking)
        let mut analysis = AnalysisPass::new(crate_name.clone());
        crate::rustc_run(&compiler_args, &mut analysis);
        let model = analysis.into_model();

        // Pass 2: Substitution (generative, after_crate_root_parsing)
        let mut intercept = CrateIntercept::new(crate_name, model);
        crate::rustc_run(&compiler_args, &mut intercept);
    } else {
        // ... existing FunctionIntercept path ...
    }
}
```

### 3.2 AnalysisPass callbacks

```rust
impl rustc_driver::Callbacks for AnalysisPass {
    fn after_expansion<'tcx>(
        &mut self,
        compiler: &Compiler,
        queries: &'tcx Queries<'tcx>,
    ) -> Compilation {
        // Access the expanded AST
        // Collect: functions, structs, enums, traits, impls, modules
        // Types recorded as TypeRepr with fully qualified paths
        // Preserve module tree structure
        Compilation::Continue  // let type checking proceed
    }

    fn after_analysis<'tcx>(
        &mut self,
        compiler: &Compiler,
        queries: &'tcx Queries<'tcx>,
    ) -> Compilation {
        // Access TyCtxt
        // Enrich model with:
        //   - All trait impls per type (including auto traits, blanket impls)
        //   - Generic parameters and bounds (lifetimes, type params, const generics)
        //   - Repr info (#[repr(C)], #[repr(transparent)], etc.)
        //   - Supertrait relationships
        //   - Associated type resolutions
        Compilation::Stop  // skip codegen, we only needed the analysis
    }
}
```

### 3.3 CrateIntercept (generative pass)

```rust
impl rustc_driver::Callbacks for CrateIntercept {
    fn after_crate_root_parsing(
        &mut self,
        compiler: &Compiler,
        krate: &mut ast::Crate,
    ) -> Compilation {
        // Step 1: Keep scaffolding, remove everything else
        krate.items.retain(|item| match &item.kind {
            ast::ItemKind::Use(..)          => true,
            ast::ItemKind::TyAlias(..)      => true,
            ast::ItemKind::Const(..)        => true,
            ast::ItemKind::Static(..)       => true,
            ast::ItemKind::ForeignMod(..)   => true,
            ast::ItemKind::MacroDef(..)     => true,
            ast::ItemKind::ExternCrate(..)  => true,
            _                               => false,
        });

        // Step 2: Recursively do the same for submodules
        //   (modules themselves are removed; they'll be regenerated)

        // Step 3: Generate entire crate body from AnalysisModel
        let source = generate_crate_from_model(&self.model);
        self.inject_source_items(compiler, krate, &source);

        Compilation::Continue
    }
}
```

## 4. The AnalysisModel

The analysis model is the bridge between the two passes. It must contain everything
needed to regenerate the crate's public API with mock dispatch bodies.

### 4.1 Top-level structure

```rust
/// Complete analysis of a crate, combining syntactic and type-level information.
pub struct AnalysisModel {
    pub crate_name: String,
    pub root: ModuleModel,
}
```

### 4.2 ModuleModel

Preserves the original module tree structure so the regenerated crate has the
same public API paths (e.g., `fns::sub_module::some_fn`).

```rust
pub struct ModuleModel {

    pub structs: Vec<StructModel>,
    pub enums: Vec<EnumModel>,
    pub traits: Vec<TraitModel>,
    pub impls: Vec<ImplModel>,
    pub children: Vec<ModuleModel>,  // nested pub mod blocks
}
```

## 5. TypeRepr — Custom Type Representation

`TypeRepr` replaces both `Box<ast::Ty>` (not serializable, tied to compiler internals)
and raw strings (no structure). It captures the shape of a type with fully qualified
paths, enabling robust code generation.

### 5.1 Definition

```rust
/// A compiler-independent representation of a Rust type.
/// All paths are fully qualified (e.g., `std::collections::HashMap`).
#[derive(Debug, Clone, PartialEq)]
pub enum TypeRepr {
    /// A simple or qualified path: `std::vec::Vec`, `Foo`, `crate::Bar`
    Path {
        segments: Vec<String>,
        generics: Vec<TypeRepr>,     // type arguments: Vec<T> → generics = [T]
    },

    /// A reference: `&T` or `&mut T`
    Reference {
        lifetime: Option<String>,
        mutable: bool,
        inner: Box<TypeRepr>,
    },

    /// A tuple: `(A, B, C)` or unit `()`
    Tuple(Vec<TypeRepr>),

    /// A slice: `[T]`
    Slice(Box<TypeRepr>),

    /// An array: `[T; N]`
    Array {
        element: Box<TypeRepr>,
        length: String,              // const expression as string
    },

    /// A raw pointer: `*const T` or `*mut T`
    RawPointer {
        mutable: bool,
        inner: Box<TypeRepr>,
    },

    /// A function pointer: `fn(A, B) -> C`
    FnPointer {
        params: Vec<TypeRepr>,
        return_type: Box<TypeRepr>,
        is_unsafe: bool,
        abi: Option<String>,
    },

    /// A dyn trait object: `dyn Trait + Send`
    DynTrait {
        bounds: Vec<TypeRepr>,
        lifetime: Option<String>,    // e.g., dyn Trait + 'a
    },

    /// An impl trait (in return position): `impl Iterator<Item = u32>`
    ImplTrait {
        bounds: Vec<TypeRepr>,
    },

    /// The never type: `!`
    Never,

    /// An inferred type: `_`
    Inferred,

    /// Self type (in trait/impl contexts)
    SelfType,

    /// A type with associated type bindings: `Iterator<Item = u32>`
    /// (Handled via Path generics + this for the bindings)
    /// Actually — associated type bindings can be part of Path generics.
    /// Reconsider whether this needs a separate variant.
}
```

### 5.2 Conversion from expanded AST

In `after_expansion`, convert `ast::Ty` → `TypeRepr` using the expanded AST where
paths have been resolved by the macro expander. Key considerations:

- **Path resolution:** After expansion, paths may include `$crate::` prefixes from
  macro hygiene. These should be resolved to actual crate paths.
- **Fully qualify standard library types:** `Vec<T>` → `std::vec::Vec<T>`,
  `String` → `std::string::String`, etc.
- **Preserve lifetime names:** `'a`, `'static`, elided lifetimes.
- **Handle `Self`:** In trait/impl context, `Self` should be recorded as `SelfType`
  or resolved to the concrete type.

### 5.3 Code generation (TypeRepr → String)

For the substitution pass, `TypeRepr` converts back to a Rust source string:

```rust
impl TypeRepr {
    pub fn to_source(&self) -> String {
        match self {
            TypeRepr::Path { segments, generics } => {
                let path = segments.join("::");
                if generics.is_empty() {
                    path
                } else {
                    let args = generics.iter()
                        .map(|g| g.to_source())
                        .collect::<Vec<_>>()
                        .join(", ");
                    format!("{}<{}>", path, args)
                }
            }
            TypeRepr::Reference { lifetime, mutable, inner } => {
                let lt = lifetime.as_ref().map(|l| format!("{} ", l)).unwrap_or_default();
                let m = if *mutable { "mut " } else { "" };
                format!("&{}{}{}", lt, m, inner.to_source())
            }
            TypeRepr::Tuple(elements) => {
                    let inner = elements.iter()
                        .map(|e| e.to_source())
                        .collect::<Vec<_>>()
                        .join(", ");
                    format!("({})", inner)
                
            }
            // ... other variants
            _ => todo!()
        }
    }

    /// Unit type shorthand
    pub fn unit() -> Self {
        TypeRepr::Tuple(vec![])
    }

    /// Whether this is the unit type
    pub fn is_unit(&self) -> bool {
        matches!(self, TypeRepr::Tuple(v) if v.is_empty())
    }
}
```

## 6. Regeneration Strategy

### 6.1 What gets kept vs. removed vs. regenerated

| AST item kind | Action | Rationale |
|---|---|---|
| `Use` | **Keep** | Name resolution scaffolding (belt-and-suspenders with fully qualified types) |
| `TyAlias` | **Keep** | May be referenced by downstream crates |
| `Const` | **Keep** | Values needed by downstream code |
| `Static` | **Keep** | May be referenced directly |
| `ForeignMod` | **Keep** | FFI declarations, no body to mock |
| `MacroDef` | **Keep** | `#[macro_export]` macros used by downstream |
| `ExternCrate` | **Keep** | Name resolution |
| `Fn` | **Remove + regenerate** | Body replaced with mock dispatch |
| `Struct` | **Remove + regenerate** | Private fields → PhantomData, add adt_mock_id |
| `Enum` | **Remove + regenerate** | Passed through from model |
| `Trait` | **Remove + regenerate** | Method signatures from model |
| `Impl` | **Remove + regenerate** | Bodies replaced with mock dispatch |
| `Mod` | **Remove + regenerate** | Rebuilt from model's module tree |
| `MacCall` | **Remove** | Macro invocations; their expanded items are in the model |

### 6.2 Module tree regeneration

The model preserves the module tree. For each `ModuleModel`, generate a `pub mod` block
containing the regenerated items for that module, recursively.

```
Model:
  root
  ├─ fn add(a: u32, b: u32) -> u32
  ├─ struct Foo { pub x: f32 }
  └─ mod sub
       └─ fn helper(s: &str) -> String

Generated:
  pub fn add(a: u32, b: u32) -> u32 { /* mock dispatch */ }
  pub struct Foo { pub x: f32 }
  pub mod sub {
      pub fn helper(s: &str) -> String { /* mock dispatch */ }
  }
  // + convenience API (PredicateAdd, ReturnAdd, on_call_add, etc.)
```

### 6.3 Mock dispatch body generation

Unchanged from the current approach — `crate_mock_gen.rs` generates mock dispatch
bodies as source strings. The difference is that it now works from `TypeRepr`
(calling `.to_source()`) instead of `pprust::ty_to_string()`.

Functions and methods with no registered mock **panic** — there is no fallback to
original implementations.

### 6.4 Convenience API injection

Also unchanged in principle — `PredicateXxx`, `ReturnXxx`, `on_call_xxx`, `expect_xxx`
wrappers are generated and injected at the crate root. The code generation uses
`TypeRepr::to_source()` for all type references.

## 7. TypeRepr: Collecting Fully Qualified Types

### 7.1 The challenge

After expansion, types in the AST are *partially* resolved. `macro_rules!` hygiene
introduces `$crate::` prefixes, and the expander resolves `use` imports within macros.
But user-written code may still use short names (`Vec<T>`, not `std::vec::Vec<T>`)
that rely on `use` statements in scope.

### 7.2 Strategy

Since we keep `use` statements in the scaffolding, short names from user-written code
will resolve correctly in the regenerated crate. For macro-generated items (where the
original `use` scope may not exist in the regenerated crate), fully qualified paths
are essential.

The conversion strategy for `ast::Ty` → `TypeRepr`:

1. **In `after_expansion`:** Walk the expanded AST. For each type, convert to `TypeRepr`.
   Use the path as-is from the expanded AST — after expansion, macro-generated paths
   are typically already resolved (`$crate::` → actual crate path).

2. **In `after_analysis`:** For types where we need full qualification (e.g., looking
   up trait impls), use `TyCtxt` to get the `DefId` and `def_path_str()` for the
   fully qualified path.

3. **Hybrid:** Collect syntactic types in `after_expansion`, then in `after_analysis`
   cross-reference with `TyCtxt` to fill in any unresolved paths. The `DefId` mapping
   (NodeId → LocalDefId → DefId) bridges the two representations.

### 7.3 Known edge cases

- **Elided lifetimes:** `fn foo(x: &str) -> &str` — lifetimes are implicit. The expanded
  AST preserves elision. The regenerated code should also use elision (not invent names).
- **`Self` in impl context:** Should be emitted as `Self` in the regenerated code (within
  impl blocks), not the concrete type.
- **Generic associated types:** `<T as Iterator>::Item` — needs the full path.
- **Closure types:** Cannot be named. Functions returning closures use `impl Fn(...)`.
  The expanded AST should already have `impl Trait` in return position.

## 8. Data Flow Between Passes

```
┌─────────────────────────────────────────────────────────────────────┐
│ AnalysisPass                                                        │
│                                                                     │
│  after_expansion:                                                   │
│    expanded AST (ast::Crate)                                        │
│    ├─ walk items recursively                                        │
│    ├─ convert ast::Ty → TypeRepr                                    │
│    ├─ collect: FunctionModel, StructModel, EnumModel, TraitModel,   │
│    │          ImplModel, MethodSigModel, GenericsModel              │
│    └─ build ModuleModel tree                                        │
│                                                                     │
│  after_analysis:                                                    │
│    TyCtxt<'tcx>                                                     │
│    ├─ for each collected struct/enum:                                │
│    │    tcx.inherent_impls(def_id) → trait impls                    │
│    │    tcx.adt_def(def_id) → repr info                             │
│    ├─ for each collected trait:                                      │
│    │    supertraits, associated types                                │
│    ├─ resolve blanket impls:                                         │
│    │    tcx.all_local_trait_impls() or similar                      │
│    └─ store enriched data on the model items                        │
│                                                                     │
│  → produces AnalysisModel (in-memory)                               │
└──────────────────────────┬──────────────────────────────────────────┘
                           │  model (owned, moved)
                           ▼
┌─────────────────────────────────────────────────────────────────────┐
│ CrateIntercept                                                      │
│                                                                     │
│  after_crate_root_parsing:                                          │
│    &mut ast::Crate (pre-expansion)                                  │
│    ├─ retain scaffolding items                                      │
│    ├─ generate source from AnalysisModel:                           │
│    │    ├─ struct definitions (with PhantomData, adt_mock_id)       │
│    │    ├─ enum definitions                                         │
│    │    ├─ trait definitions                                        │
│    │    ├─ impl blocks (mock dispatch bodies)                       │
│    │    ├─ free functions (mock dispatch bodies)                    │
│    │    ├─ pub mod blocks (recursive, preserving module tree)       │
│    │    └─ convenience API (Predicate*, Return*, on_call_*, etc.)  │
│    └─ inject parsed items into krate.items                          │
│                                                                     │
│  → Compilation::Continue (rustc handles expansion, resolution,      │
│    type checking, codegen of the regenerated crate)                 │
└─────────────────────────────────────────────────────────────────────┘
```

## 9. Matching Items Between after_expansion and after_analysis

Items collected in `after_expansion` (from the expanded AST) need to be matched
with their typed representations in `after_analysis` (from `TyCtxt`).

### Primary key: DefId

Every item in the expanded AST has a `NodeId`. The compiler assigns `LocalDefId`
values during expansion. In `after_analysis`, the same items are accessible via
`DefId` in `TyCtxt`.

**Strategy:**
1. In `after_expansion`, record each item's `NodeId` alongside the syntactic model.
2. In `after_analysis`, use `tcx.hir().node_to_hir_id(node_id)` or equivalent to
   look up the item's `DefId`.
3. Use the `DefId` to query `TyCtxt` for type-level information.

**Fallback:** Match by fully qualified path (crate::module::ItemName). Works for
all cases without name collisions within a module (which is guaranteed by Rust's
name resolution rules).

- `anomura_plugins` pipeline (discover pass, cargo-mock binary, IPC)

  Add `GenericsModel`, `ReprInfo`, `TraitImplInfo`. Remove `Derives` struct
  (replaced by `TraitImplInfo` from actual expanded impls).

  Simplify to: receive model, retain scaffolding, regenerate from model.

  `pprust::ty_to_string()`. Logic otherwise unchanged.
- **`substitution_pass.rs`** — Add analysis pass invocation before CrateIntercept.
  Add `AnalysisPass` struct (new file or in `crate_intercept.rs`).

  `after_expansion` + `after_analysis` callbacks.
- **`type_repr.rs`** — `TypeRepr` enum, conversion from `ast::Ty`, `to_source()`.
- **`generics_model.rs`** (or part of `crate_api.rs`) — `GenericsModel`,
  `LifetimeParam`, `TypeParam`, `ConstParam`, `WherePredicate`.

## 12. Risk Assessment

| Risk | Severity | Mitigation |
|------|----------|------------|
| `after_expansion` callback API changes | Medium | Pinned nightly; check on updates |
| Expanded AST type paths not fully qualified | Medium | Cross-reference with TyCtxt in after_analysis; keep `use` scaffolding as fallback |
| Two compilations per mock_crate target | Low | Analysis pass stops before codegen; acceptable latency for test workflow |
| TypeRepr doesn't cover all Rust type syntax | Medium | Start with common types, extend as needed. `to_source()` can fall back to string for edge cases |
| Scaffolding items reference removed items | Low | Scaffolding items (use, const, type alias) reference types/values, not fn bodies. Types are regenerated from model. |
| rustc_run called twice with same args in same process | Low | Each invocation creates fresh compiler state. Verified by existing patterns (CompileMocks + FunctionIntercept). |
| Module-private items referenced by public items | Medium | Analysis pass collects all items visible after expansion; private items used by public APIs need to be in the model. Consider collecting `pub(crate)` items too. |

## 13. Resolved Questions

1. **`pub(crate)` and restricted visibility items.** Items with restricted visibility
   (`pub(crate)`, `pub(super)`, etc.) are **excluded** from the model. Only fully public
   items are collected and regenerated. Restricted-visibility items are not part of the
   external API and should not cause issues when removed.

2. **Trait method default implementations.** Default bodies are **not preserved**. All
   trait methods in the regenerated crate get **default mock dispatch bodies** inserted
   by the code generator. See section 14 for full trait handling design.

3. **Constants and statics.** Public constants and statics are **kept as-is** from the
   original source (scaffolding). Private ones are removed.

## 14. Trait Handling Design

Traits require special attention because mock expectations need to work both on
concrete types and on trait objects (`dyn Trait`).

### 14.1 Basic trait regeneration

- **Private traits:** Kept but all methods removed (empty trait body). This preserves
  trait bounds without exposing implementation details.
- **Public traits:** Kept with all method signatures. Default method bodies are replaced
  with mock dispatch defaults.

### 14.2 Trait-level vs type-level mocking

When a concrete type `Circle` implements `Drawable`, there are two distinct mock points:

```rust
// Type-level: mock Circle::draw specifically
circle.on_call_draw(|_self| true, |_self| "mocked circle".to_string());

// Trait-level: mock Drawable::draw for any dyn Drawable
// (sets default behavior for the trait method itself)
```

Both should be supported. The impl block for `Circle` gets mock dispatch that checks
for instance-specific mocks first, then falls back to trait-level mocks.

### 14.3 The trait object problem (instanced vs non-instanced)

When a concrete type is accessed through `&dyn Trait`, the mock dispatch loses access
to the concrete type's `adt_mock_id`. This creates a problem for instance-specific
mocking through trait objects.

**Instanced types** (structs with private fields → `adt_mock_id` field):
- Full instance-specific mocking works on the concrete type.
- Through `dyn Trait`, the `adt_mock_id` is inaccessible (vtable dispatch only sees
  trait methods).

**Non-instanced types** (all-public structs → no `adt_mock_id`):
- Path-only mock IDs (shared, not per-instance).
- Same limitation through trait objects.

**Proposed solution:** A marker trait `NonInstancedMock` (or similar) with a method
that returns an ADT signifier. A blanket impl for `Trait` where `Self: NonInstancedMock`
provides the ID extraction. This allows trait object dispatch to recover mock identity.

```rust
// Generated marker trait
pub trait MockIdentity {
    fn mock_identity(&self) -> context::MockIdentifier;
}

// For instanced types: return the adt_mock_id
impl MockIdentity for Circle {
    fn mock_identity(&self) -> context::MockIdentifier {
        context::MockIdentifier::Instance(self.adt_mock_id)
    }
}

// For non-instanced types: return the type-level ID
impl MockIdentity for Point {
    fn mock_identity(&self) -> context::MockIdentifier {
        context::MockIdentifier::Static("fns_Point")
    }
}
```

The trait method dispatch can then attempt to recover the mock identity:
1. Check if the trait object also implements `MockIdentity` (via `Any`-like downcasting
   or a supertrait bound).
2. If yes, use the instance/type-level mock ID for targeted dispatch.
3. If no, fall back to trait-level mock dispatch.

> **Note:** The exact mechanism for recovering mock identity through trait objects is
> a design area that needs further prototyping. The key insight is that we want mock
> expectations to be settable at both the trait level and the concrete type level,
> with trait objects gracefully falling back to trait-level mocks when type identity
> is unavailable.

## 15. Remaining Open Questions

1. **Generic impl blocks.** `impl<T: Clone> Foo<T> { fn bar(&self) -> T { ... } }` — the
   generics on the impl block need to be captured and regenerated. The `GenericsModel`
   on `ImplModel` handles this, but the code generation needs to emit them correctly.

2. **Orphan rules.** The regenerated crate implements traits for its own types. Since the
   trait impls come from the same crate, orphan rules should be satisfied. But blanket
   impls from external crates (e.g., `impl<T: Display> ToString for T`) don't need to
   be regenerated — they apply automatically.

3. **Conditional compilation.** Items behind `#[cfg(feature = "...")]` are resolved during
   expansion (the analysis pass sees only the items that match the active cfg). The
   substitution pass should use the same feature flags. Since both passes use the same
   `compiler_args`, this should be automatic.

4. **Trait object mock identity recovery.** The exact mechanism for extracting mock
   identity from `dyn Trait` objects needs prototyping. Supertrait bounds
   (`trait Drawable: MockIdentity`) would work but modify the trait's public API.
   Alternative approaches (e.g., storing identity in thread-local state keyed by
   raw pointer) need investigation.
